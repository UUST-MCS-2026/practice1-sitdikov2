\# Заметки по Git



Шаг 5. Три эксперимента



&#x20;А. Пустая папка

1\. Пустая папка `sandbox` не появилась в репозитории. Git не отслеживает пустые папки, потому что хранит информацию только о файлах (блобах), а папки для него — это просто часть пути к файлу.

2\. Чтобы папка оказалась в репозитории, я создал внутри неё файл `empty.txt`. После этого Git увидел новый путь и добавил его в индекс.



&#x20;Б. Исчезнувший файл

1\. Файл `about/secret.txt` исчез из текущей версии проекта (его нет в рабочей директории), но он остался в репозитории — в истории коммитов.

2\. Команда, показывающая содержимое удалённого файла: `git show <хэш\_коммита>:about/secret.txt`. Она вывела текст «мой супер-пароль 123».

3\. Это значит, что если случайно закоммитить пароль, а потом удалить файл, пароль всё равно останется в истории Git навсегда. Любой, кто склонирует репозиторий, сможет найти его через историю. Поэтому при утечке пароля его нужно сразу менять.



&#x20;В. Мусор и .gitignore

1\. Одного `.gitignore` оказалось недостаточно, потому что файлы `output.log` и `\_\_pycache\_\_` уже были добавлены в репозиторий (отслеживались Git). `.gitignore` работает только для новых, ещё не отслеживаемых файлов.

2\. Дополнительно понадобились команды `git rm --cached output.log` и `git rm -r --cached \_\_pycache\_\_`. Они удаляют файлы из индекса Git (перестают отслеживать), но оставляют их физически на диске.



Шаг 6. Внутри .git

1\. Создал два файла с одинаковым содержимым и закоммитил. В `.git/objects` появился один новый объект. Git хранит данные по хэшу содержимого (blob). Если содержимое одинаковое, создаётся только один объект, чтобы не дублировать данные.

2\. Выполнил `git hash-object <файл>` до коммита. Результат совпал с именем объекта после коммита. Потому что Git использует SHA-1 хэш от содержимого файла для именования объектов. `git hash-object` просто вычисляет этот хэш.

3\. Изменил один символ в файле и закоммитил. Старые деревья и файлы не исчезли - они остались в истории. Два других файла, которые я не трогал, остались теми же объектами (их хэши не изменились). Это говорит о том, что Git хранит снимки, но использует дедупликацию: если файл не менялся, он переиспользуется. Изменится только один blob, все деревья по пути к нему и сам коммит.



Шаг 7. Коммит без git commit

1\. Что делает каждая команда:

&#x20;  - `hash-object -w` - записывает объект (blob) в базу данных Git.

&#x20;  - `update-index --add` - добавляет объект в индекс (staging area).

&#x20;  - `write-tree` - создаёт объект дерева (tree) из текущего индекса.

&#x20;  - `commit-tree` - создаёт объект коммита, указывающий на дерево.

&#x20;  - `update-ref` - создаёт ссылку (ветку `main`), указывающую на коммит.

2\. После `git write-tree` команда `git status` показывает чистое дерево, потому что `write-tree` синхронизирует индекс (staging) с базой данных объектов. `git status` сравнивает рабочую директорию с индексом, а так как мы обновили индекс, статус чист. `git commit` — это просто обёртка, которая делает эти же шаги автоматически.

3\. Объекты (blob, tree, commit) появились на этапах `hash-object -w`, `write-tree`, `commit-tree`. Ссылка (ref) появилась на последнем шаге `update-ref` (до этого ветка `main` не существовала).
